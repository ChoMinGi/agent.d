# 작성 메모

두 번째 세트 역시 어떤 추출 결과도 보지 않은 상태에서 독립적인 가상 프로젝트로 구성했다. 첫 세트의 정답을 변환해 만들지 않았으며 외부 서비스나 실제 사람의 자료는 사용하지 않았다. 문서와 기대 의미를 한 작성자가 일관되게 정의하되 추출기의 구현, 기존 저장소, 이전 프롬프트와 평가 세트는 열람하지 않았다.

옛 회의에서 연결 없는 저장을 막았다는 것은 역사적 사실이지만 현재 요청의 규칙이 아니다. 최신 문서가 이를 폐기했으므로 바뀐 범위를 설명하는 짧은 언급은 허용하되 옛 안을 실행해야 할 요구로 제시하면 실패다. 다중 기기 충돌과 사진 자동 전송은 과거에도 승인된 기능이 아니었다.

주장과 관찰의 차이가 중요하다. 고객 기록은 본인의 회상이고, 산새첩은 공개 시연의 한 경로이며, 들빛노트는 소개문만 읽었다. 출처별 한계를 남긴다면 market_evidence로 묶거나 question으로 남긴 항목을 분리하는 등 표현은 유연하게 인정한다. 소개문에 기능이 있다는 사실을 observed로 부르더라도 제품 동작을 직접 검증한 것으로 오해하지 않게 써야 한다.

기기에 보관된 관찰과 서버 반영, 로그인과 연결, 정상 종료와 특정 순간 강제 종료는 구별해야 한다. 기기 목록 중복은 서버 중복과 다르다. 재전송에서 서버 중복이 없었다는 관찰이 식별자 설계 전반 또는 모든 종료 경계의 검증을 뜻하지 않는다.

b-f16은 필수 입력 검증과 로컬 우선 저장을 결합한다. 별도 사실로 나누거나 관련 요구와 함께 제시해도 의미가 보존되면 인정한다. b-f26의 unverified는 위험 및 설계 의도가 알려져 있지만 특정 실행 검증이 없다는 뜻이다. risk/open 또는 test_case/planned처럼 적절한 표현으로 이를 전달해도 공정하게 평가한다. b-f27은 문구 미정인 질문과 향후 제안 작업을 결합했으므로 각각 분리할 수 있다.

required_for는 최소 문맥 의미이지 항목 수나 문장 순서를 지정하지 않는다. allowed_for에 든 내용은 합리적 추가 맥락이다. allowed_for가 빈 옛 안·타 프로젝트 사실은 독립 근거로 포함하지 않는 것이 목표다. 제공 근거를 바탕으로 새 시험을 제안할 수 있지만 제안 상태를 명확히 밝혀야 하며 이미 수행된 시험이나 확정된 요구로 표시하면 안 된다.
